## MARKER 1 — Cron auto-re-registration masks root causes

### Initial Finding
`metamanager.php` `mm_activate_single_site()` (lines 206-219) calls `wp_schedule_event()` with `wp_next_scheduled()` guard on every plugin update (activation re-runs). If an admin deliberately removes a cron event to troubleshoot, the next update silently re-adds it.

### Applicable Rules
**Rule 9** (AGENTS.md line 73): *"WordPress cron must NEVER be re-registered on page load, init, admin_init, or any request hook — WP-Cron events are stored in the database via `wp_schedule_event()` and persist across requests and reboots. If a cron event is missing, investigate WHY it was removed — do not re-register it on every request."*

**Rule 15** (AGENTS.md line 85): *"Do not manually configure things that the code should handle."*

**Rule 18** (AGENTS.md line 91): *"No fallbacks — Missing configuration must fail loudly. Defaults live only in config-template.json and migrate-template.json, never scattered in code. Never add a silent fallback (default values in functions, `|| true`, suppressed errors) to make something work — fix the code or fix the config path. Default-in-code hides breakage."*

**`metamanager-plugin/AGENTS.md`**: *"Activation hook registers cron. This is correct — cron registration belongs at activation."* (Note: the plugin AGENTS.md says activation is OK, but the workspace rule 9 says "never on any request hook" and "investigate WHY." The plugin AGENTS.md itself acknowledges this tension in its comment.)

### Related Code
- `metamanager.php:206-219` — `mm_activate_single_site()` schedules 3 cron events
- `metamanager.php:216` — comment: *"a missing event gets investigated, not masked"*
- `metamanager.php:321-325` — `mm_deactivate_site()` clears all cron events
- `metamanager-plugin/AGENTS.md` — activation hook documentation

### Diagnosis
The `wp_next_scheduled()` guard prevents *duplicate* scheduling but NOT *re-scheduling after deliberate removal*. If an admin runs `wp cron event delete mm_import_completed_jobs` to debug, the next plugin update re-schedules it. The code comment at line 216 says "investigated, not masked" but the code does the opposite: it masks by auto-fixing. This is rule 9 in spirit (not letter — the rule says "never on request hooks" and activation is technically not a request hook) but violates the INTENT: investigate why cron is missing, don't auto-fix.

**Split-brain**: Plugin AGENTS.md says "activation is correct" while workspace AGENTS.md rule 9 says "investigate WHY." These contradict.

### Relationships
- Related to Marker 2 (silent job suppression): if cron is re-registered, suppressed jobs go unprocessed without anyone knowing why.
- Related to Marker 3 (transient lock): the lock suppresses processing if cron crashes, and auto-re-registration hides the crash.

### Proof of Assumptions
- **Assumption**: Plugin updates re-run `mm_activate`. **Proof**: WordPress re-runs `register_activation_hook` callbacks on plugin version change. `mm_activate()` calls `mm_activate_single_site()` which calls `wp_schedule_event()`. Verified in code at lines 185-192.
- **Assumption**: `wp_next_scheduled()` prevents duplicate scheduling. **Proof**: WordPress docs — `wp_next_scheduled()` returns timestamp if event exists. The `if` block only fires when it returns `false`. Verified at line 206.

## MARKER 2 — Silent job suppression presented as feature

### Initial Finding
`class-mm-job-queue.php` `write_job()` silently drops compression jobs when a duplicate is pending. `class-mm-admin.php:117` shows users "duplicate compression suppressed" in the UI as if intentional.

### Applicable Rules
**Rule 18** (AGENTS.md line 91): *"No fallbacks — Missing configuration must fail loudly. Never add a silent fallback (default values in functions, `|| true`, suppressed errors) to make something work."*

**Rule 14** (AGENTS.md line 83): *"Failure to get a response is not evidence — A timeout, empty response, or connection failure does not confirm anything."* — The suppression assumes the existing job will succeed. That's an assumption without evidence.

### Related Code
- `class-mm-job-queue.php:119-142` — type-aware duplicate detection, returns `'skipped'`
- `class-mm-job-queue.php:132` — comment: *"Compression: skip duplicate. Metadata: write anyway"*
- `class-mm-admin.php:117` — UI text: *"duplicate compression suppressed, metadata queued in sequence"*
- `class-mm-job-queue.php:103-104` — docblock: *"'skipped' — compression duplicate found; write suppressed."*

### Diagnosis
The code reads every pending `.json` file and checks `job_type`. If a matching job exists, the new job is silently dropped. The admin UI tells the user it was "suppressed" — presenting data loss as a feature. The duplicate check assumes the pending job will complete successfully. If it fails (daemon crash, file error), the new job was dropped AND the old one failed = zero jobs done, zero errors reported.

**Rule 18 violation**: The suppression is a silent fallback that makes the system "work" by dropping work instead of queuing it and letting the daemon deduplicate at processing time.

**Rule 14 violation**: The code assumes "pending job exists = it will succeed." No evidence of that.

### Relationships
- Related to Marker 1: if cron is re-registered after deliberate removal, suppressed jobs sit forever.
- Related to Marker 3: if the transient lock suppresses processing, dropped jobs never get a second chance.
- Related to Marker 37 (O(n) JSON parsing): the duplicate detection reads every pending file on every write.

### Proof of Assumptions
- **Assumption**: Pending jobs will eventually process successfully. **Proof needed**: No code tracks job outcome after queuing. If daemon crashes after `write_job()` returns 'written' but before processing, the job is lost. The `mm_import_completed_jobs` cron only processes result files — it doesn't check if queued jobs ever produce results.
- **Assumption**: Dropping the new job is safe because the old one is equivalent. **Proof**: Only `attachment_id` and `size` are compared. If the old job was queued with different `metadata` or `trigger`, the new job's parameters are lost.

## MARKER 3 — Transient lock suppresses processing on crash

### Initial Finding
`metamanager.php:485-489` — `mm_import_completed_jobs()` uses a transient lock with 30-second timeout. If the function crashes mid-run, the lock persists until the transient expires. The next run returns early (line 487: `if ( get_transient( $lock_key ) ) return;`). Zero error output.

### Applicable Rules
**Rule 18** (AGENTS.md line 91): *"No fallbacks — Never add a silent fallback (default values in functions, `|| true`, suppressed errors) to make something work."*

**Rule 14** (AGENTS.md line 83): *"Failure to get a response is not evidence."* — The code treats "lock exists" as "another run is active." But the lock could exist because of a crash. Absence of a running process is not evidence of one.

### Related Code
- `metamanager.php:485-486` — `if ( get_transient( $lock_key ) ) return;`
- `metamanager.php:489` — `set_transient( $lock_key, 1, 30 )`
- `metamanager.php:494` — `delete_transient( $lock_key )` (memory gate path)
- `metamanager.php:646` — `delete_transient( $lock_key )` (end of function)

### Diagnosis
The transient lock is a concurrency guard. But it conflates "another run is active" with "a previous run crashed." The only way to release the lock after a crash is waiting 30 seconds. During that time, result files pile up. No error is logged, no alert fires, no retry happens.

**Rule 18 violation**: The lock is a silent fallback — it makes the system "work" by suppressing work instead of detecting the crash and recovering.

**Proof of gap**: If `mm_import_completed_jobs()` throws a PHP fatal at line 550, `delete_transient` at line 646 never runs. The lock holds for 30 seconds. The next cron run at +60s finds the lock and returns. That's 30 seconds of silent suppression.

### Relationships
- Related to Marker 1: cron auto-re-registration masks the crash from the admin.
- Related to Marker 2: jobs suppressed by duplicate detection never get re-evaluated after the lock expires.
- Related to Marker 4: DB failure `continue` at line 547 also leaves the lock held until function end.

### Proof of Assumptions
- **Assumption**: The lock prevents concurrent execution. **Proof**: PHP is single-threaded per request. WP-Cron can fire multiple times if page loads are frequent. The transient lock is the correct mechanism — but it needs crash detection, not just expiry.
- **Assumption**: 30 seconds is enough for a normal run. **Proof needed**: No timing measurement exists. If processing 500 result files takes >30 seconds, the lock expires mid-run and a concurrent cron could start.

### Initial Finding
`metamanager.php:546-549` — When `MM_DB::log_job()` fails, the result file is left in place and the code does `continue`. The comment says "will retry on next cron run." No max retries, no escalation, no dead-letter queue.

### Applicable Rules

**Rule 14** (AGENTS.md line 83): *"Failure to get a response is not evidence."* — The code assumes the next cron run will succeed. No evidence.

### Related Code

- `metamanager.php:533` — `if ( ! MM_DB::log_job( $job ) )` — the check
- `class-mm-db.php` — `log_job()` implementation

### Diagnosis
If `log_job()` fails persistently (disk full, table corrupt, permissions wrong), the result file is left in place. Every 60 seconds, `mm_import_completed_jobs` reads it, tries `log_job()`, fails, `continue`s. This loops forever with no escalation. The file is never moved to a dead-letter directory. No error is sent to the admin. The cron history tracker records the run but not the failure.

**Rule 18 violation**: "Will retry on next cron run" is a silent fallback. The code should fail loudly — log the error, move the file to a `failed-log` directory after N attempts, or send an admin alert.

### Relationships
- Related to Marker 3: the transient lock is released at function end even if DB writes failed, so the retry does happen — but only 1 attempt per minute, forever.
- Related to Marker 1: if cron is re-registered after removal, the retry continues even if the admin wanted to stop it.

### Proof of Assumptions
- **Assumption**: The next cron run will retry. **Proof**: The file is left in `completed/` directory. `mm_import_completed_jobs` scans `completed/` on each run. Verified — the `GlobIterator` at line 513 picks up all `.json` files. But: if `log_job()` keeps failing, the file is read and discarded (line 648 `wp_delete_file`) ONLY after successful insert. On failure, `continue` skips the delete. So the file persists. **But there's no max retry counter** — the loop is unbounded.

## MARKER 5 — Memory manager bail-out hides real memory issues

### Initial Finding
`class-mm-memory-manager.php:190` — `return false; // Unlimited PHP, no system data — don't pause.` When PHP has no memory limit set (`memory_get_usage` returns false or system has no `/proc/meminfo`), the memory manager silently doesn't pause. Real memory problems go undetected.

### Applicable Rules
**Rule 18** (AGENTS.md line 91): *"No fallbacks — Missing configuration must fail loudly. Defaults live only in config-template.json and migrate-template.json, never scattered in code. Never add a silent fallback (default values in functions, `|| true`, suppressed errors) to make something work — fix the code or fix the config path. Default-in-code hides breakage."*

**Rule 14** (AGENTS.md line 83): *"Failure to get a response is not evidence — A timeout, empty response, or connection failure does not confirm anything."* — "Can't measure" is not "memory is fine."

### Related Code
- `class-mm-memory-manager.php:178-211` — `should_pause()` method
- `class-mm-memory-manager.php:190` — `return false; // Unlimited PHP, no system data`
- `class-mm-memory-manager.php:96` — `memory_get_usage( true )`
- `metamanager.php:491-495` — `MM_Memory_Manager::should_pause()` call in `mm_import_completed_jobs()`

### Diagnosis
The method checks if PHP has a memory limit and if `/proc/meminfo` is readable. If neither is available, it returns `false` (don't pause). This means: if the system is out of memory but PHP has no limit and `/proc/meminfo` is unreadable, processing continues into a potential OOM crash. The comment says "don't pause" but the real issue is "can't tell if we should pause" — which should fail loudly per rule 18.

**Rule 18 violation**: Returning `false` (don't pause) is a silent default. The code should either fail loudly ("cannot determine memory status") or use a safe default (pause).

### Relationships
- Related to Marker 3: if memory manager says "don't pause" but memory IS low, `mm_import_completed_jobs` proceeds and could crash, triggering the transient lock suppression.

### Proof of Assumptions
- **Assumption**: PHP with no memory limit means "unlimited memory." **Proof needed**: `ini_get('memory_limit')` returning `-1` means no limit, but the OS can still OOM-kill the process. The code conflates "PHP won't enforce a limit" with "memory is available."

## MARKER 7 — WebP registration triggers recursive WebP job queuing

### Initial Finding
`metamanager.php` `mm_register_webp_attachment()` calls `wp_generate_attachment_metadata()` (line ~447). This fires the `wp_generate_attachment_metadata` filter, which is hooked by `MM_Job_Queue::on_upload()` (line 335). `on_upload()` sees the WebP file as an image and calls `enqueue_all_sizes( ..., 'compress+webp', ... )`. **The WebP file gets queued for WebP generation.**

### Applicable Rules
**Rule 18** (AGENTS.md line 91): *"No fallbacks — Never add a silent fallback to make something work."*

**Rule 15** (AGENTS.md line 85): *"Do not manually configure things that the code should handle."* — The code should handle WebP files correctly in `on_upload()`.

### Related Code
- `metamanager.php` `mm_register_webp_attachment()` — calls `wp_generate_attachment_metadata()`
- `class-mm-job-queue.php:334-337` — `if ( $is_image ) { ... enqueue_all_sizes( ..., 'compress+webp', ... ) }`
- `class-mm-job-queue.php:323` — `wp_attachment_is_image( $attachment_id )` returns true for WebP
- `class-mm-job-queue.php:275` — `enqueue_all_sizes` signature

### Diagnosis
`mm_register_webp_attachment()` registers a WebP as a WP attachment and calls `wp_generate_attachment_metadata()` to generate sizes. This triggers `on_upload()` which queues compression + webp jobs for the WebP file. The daemon would then:
1. Try to compress the WebP (lossless — wasteful but harmless)
2. Try to generate `image.webp.webp` (or `image.webp` from `image.webp` — the `preg_replace` in the webp job would match `.webp` and produce `image.webp`)

The result is wasted daemon cycles and potential file confusion.

**Rule 18 violation**: The code doesn't handle the WebP case — it silently queues unnecessary jobs.

### Relationships
- Related to Marker 2: the duplicate detection would suppress the second WebP job, but the first one still processes.

### Proof of Assumptions
- **Assumption**: `wp_attachment_is_image()` returns true for WebP. **Proof**: WordPress `wp_attachment_is_image()` checks `wp_attachment_is('image', $post)` which matches any `image/*` mime type. `image/webp` matches. Verified.

## MARKER 13 — save_meta race condition during page regeneration

### Initial Finding
`class-mm-page-generator.php:62-77` `regenerate_page()` removes `save_meta` hook (line 64), calls `wp_update_post()` (line 69), re-adds hook (line 75). If any other plugin or WP-Cron fires `save_post` during the gap, `save_meta` is never called.

### Applicable Rules
**Rule 18** (AGENTS.md line 91): *"No fallbacks — Never add a silent fallback."*

**Rule 8** (AGENTS.md line 71): *"Never break or dismantle when failing to diagnose."* — Removing the hook is altering behavior as a workaround.

### Related Code
- `class-mm-page-generator.php:62-77` — `regenerate_page()`
- `class-mm-page-generator.php:64` — `remove_action( 'save_post', [ 'MM_Schema_Post_Types', 'save_meta' ], 10 )`
- `class-mm-page-generator.php:75` — `add_action( 'save_post', [ 'MM_Schema_Post_Types', 'save_meta' ], 10, 2 )`
- `class-mm-schema-post-types.php:47` — `add_action( 'save_post', [ __CLASS__, 'save_meta' ], 10, 2 )`

### Diagnosis
The hook is removed to prevent infinite loop (`wp_update_post` inside `save_meta` would trigger `save_meta` again). But removing the hook globally means ANY `save_post` during the window loses `save_meta`. The correct fix is to use a flag (`$this->saving = true`) or check `DOING_AUTOSAVE` inside `save_meta` to prevent recursion, not remove the hook.

**Rule 18 violation**: Removing the hook is a silent fallback that prevents recursion but creates a race condition.
